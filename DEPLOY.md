# Deploying FitForge

| Piece | Where | Why |
| --- | --- | --- |
| Database | MongoDB Atlas | Already in use. Production gets its **own** database. |
| API (`backend/`) | Render (Docker) | `render.yaml` describes it. |
| Website (`frontend/`) | Vercel | Built for Next.js. Forwards `/api/*` to the API, so login cookies stay first-party. |
| Uploads | AWS S3 | Render's disk is wiped on every deploy. |
| Email | Resend (or any SMTP provider) | Password reset links. |
| Error tracking | Sentry (optional) | Server errors with stack traces. |
| Uptime | UptimeRobot or Better Stack (free) | Alerts you when the site or database is down. |

Do the steps in order. Nothing here needs a code change.

## 1. Atlas: a separate production database and user

Development data (demo accounts with the public password `Password123!`) must never reach
production, so production uses a different database in the same cluster.

1. **Database Access → Add New Database User**, e.g. `fitforge-prod`, with an autogenerated
   password and the role **readWrite** on the database `fitforge_prod` only (Specific Privileges).
2. Your production `MONGO_URI` is the cluster's connection string with that user and
   `/fitforge_prod` before the `?`:
   `mongodb+srv://fitforge-prod:<password>@cluster0.xxxxx.mongodb.net/fitforge_prod?retryWrites=true&w=majority`
3. Network access is tightened in step 6, once Render tells you its addresses.

Never run `npm run seed` against production. The seed scripts refuse `NODE_ENV=production`
and remote databases without `--yes`. As a backstop, on a live deployment (production mode on a
public address) demo `@fitforge.dev` accounts can't sign in or sign up, and the API logs a warning
at startup if any exist in its database.

## 2. Email: Resend

1. Create an account at resend.com → **Domains → Add Domain** (e.g. `mail.yourdomain.com`), and add
   the DNS records it shows at your domain registrar. Wait until it says **Verified**.
2. **API Keys → Create API Key** with *Sending access*. It starts with `re_`. Keep it for step 4.
3. `MAIL_FROM` must use the verified domain, e.g. `FitForge <no-reply@mail.yourdomain.com>`.

No domain yet? For a first test use `MAIL_FROM=FitForge <onboarding@resend.dev>`. Resend then
only delivers to the email address you signed up with.

Prefer another provider? Leave `RESEND_API_KEY` empty and set `SMTP_URL`
(e.g. `smtps://user:password@smtp-relay.brevo.com:465`).

## 3. Uploads: S3

Create a private bucket (Block all public access: on) in `ap-south-1`, and an IAM user limited to
`s3:PutObject`, `s3:GetObject` and `s3:DeleteObject` on that bucket. Keep its access keys for step 4.

## 4. API on Render

1. Render dashboard → **New → Blueprint** → pick the GitHub repository and the branch you deploy
   from. It reads `render.yaml`.
2. Fill in the values marked `sync: false`:
   - `MONGO_URI`: the production string from step 1.
   - `CLIENT_ORIGIN` and `APP_URL`: the website address, e.g. `https://fitforge.vercel.app`.
     (Deploy the website first, or use a guess and update both later.) Must be `https://`.
   - `RESEND_API_KEY` and `MAIL_FROM` from step 2.
   - `AWS_S3_BUCKET`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` from step 3.
   - `SENTRY_DSN`: optional, see step 7.
3. `JWT_ACCESS_SECRET` is generated for you, fresh and different from development. Changing it
   later signs everyone out.
4. When it's live, `https://<your-api>.onrender.com/api/health` returns
   `{"status":"ok","database":"ok"}`.

The API checks its own settings when it starts. It **refuses to start** if `JWT_ACCESS_SECRET` looks
like a placeholder or the site addresses aren't `https://`, and the Render log says which setting
is wrong. It **starts but warns** in the log when email, S3 or Sentry isn't set up.

## 5. Website on Vercel

1. Vercel → **Add New → Project** → the repository. Set **Root Directory** to `frontend`.
2. Environment variables (used at build time, so redeploy after changing them):
   - `API_URL` = `https://<your-api>.onrender.com`
   - `NEXT_PUBLIC_APP_URL` = the website's own address (the front-desk QR code uses it).
   - `NEXT_PUBLIC_HERO_VIDEO_URL` (optional) = a landing video you own, e.g. `/hero.mp4`.
3. Deploy, then set `CLIENT_ORIGIN` and `APP_URL` on Render to the final website address.

## 6. Lock Atlas network access to Render

Rather than allowing `0.0.0.0/0` (anyone on the internet), allow only Render:

1. Render → your API service → **Connect → Outbound** lists the IP ranges its traffic comes from.
2. Atlas → **Network Access → Add IP Address**: add each range. Comment: `Render API`.
3. Remove `0.0.0.0/0` if it's there. Keep your own IP only while you need it, and remove it after.
4. Check `/api/health` still shows `"database":"ok"`.

## 7. Monitoring and backups

- **Error tracking:** create a free Sentry project (platform: Node.js), copy its **DSN**, and set
  `SENTRY_DSN` on Render. Unexpected server errors (anything that becomes a 500) are reported with
  the route and user id. Request bodies, cookies and query strings are never sent.
- **Uptime:** in UptimeRobot or Better Stack, add an HTTP monitor for
  `https://<site>/api/health` every 5 minutes. It fails (503) when the API is up but can't reach the
  database, so it covers the website, the API and Atlas in one check.
- **Backups:** the free Atlas tier (M0) has no automatic backups. On a paid tier, turn on
  **Backup** for the cluster and check a restore once. Until then, take a manual copy before risky
  changes:
  `mongodump --uri "<production MONGO_URI>" --out backup-$(date +%F)`.

## 8. Strava (optional)

Members can link Strava from **Profile → Connected apps**; every workout they finish then appears
on Strava as a Weight Training activity.

1. Strava requires a subscription to create an API app. Signed in to Strava, open
   **https://www.strava.com/settings/api** and create an app:
   - **Application name:** FitForge (Strava's rules: don't put "Strava" in your app's name)
   - **Category:** Training · **Website:** your website address
   - **Authorization Callback Domain:** your website's domain only, e.g. `fit-forge-dev.vercel.app`
     (no `https://`, no path). For local testing use `localhost`.
2. Copy the **Client ID** and **Client Secret** into Render: `STRAVA_CLIENT_ID`, `STRAVA_CLIENT_SECRET`.
   `TOKEN_ENCRYPTION_KEY` is generated by Render; it encrypts the Strava tokens in the database.
   Changing it later disconnects everyone from Strava (they just connect again).
3. **Save, rebuild, and deploy.** The card appears on members' Profile pages.

New Strava apps start in **single-player mode**: only your own Strava account can connect. In
Strava's API settings you can raise that to 10 athletes; beyond that, Strava reviews the app
(they ask for screenshots of the "Connect with Strava" button and of Strava data in the app).

## 9. First login

Production starts empty. Open the website, choose **Get started → I own a gym**, and create the real
owner account. Add trainers and staff from **Team**. Members join with the gym code, or the owner
adds them there.

## Checklist

- [ ] `https://<site>/api/health` shows `{"status":"ok","database":"ok"}`.
- [ ] Render log shows no `Unsafe production configuration` and no warnings you didn't expect.
- [ ] Sign up, log out, log in. Cookies are `Secure` and `HttpOnly` (browser devtools → Application).
- [ ] `owner@fitforge.dev` / `Password123!` does **not** sign in.
- [ ] Forgot password sends a real email, and its button opens the website.
- [ ] Upload a profile photo; it survives a Render redeploy (it's in S3).
- [ ] Front-desk QR code shows the website address, and scanning it on a phone checks in.
- [ ] Atlas: production uses `fitforge_prod` with its own user, and Network Access has no `0.0.0.0/0`.
- [ ] Uptime monitor is green, and a test error appears in Sentry (if set up).

## Running the whole stack in Docker

```bash
JWT_ACCESS_SECRET=$(node -e "console.log(require('crypto').randomBytes(48).toString('hex'))") \
  docker compose --profile full up --build
```

The website is on http://localhost:3000 (set `WEB_PORT` for another port) with its own MongoDB.
Uploads go to a Docker volume. Because the site is on `localhost`, the production checks are relaxed
here.

## Settings reference (API)

| Variable | Required | Notes |
| --- | --- | --- |
| `MONGO_URI` | yes | Production: its own database (`/fitforge_prod`) and user. |
| `JWT_ACCESS_SECRET` | yes | 32+ random characters. No placeholders in production. |
| `APP_URL` | in production | Website address for emailed links. `https://` in production. |
| `CLIENT_ORIGIN` | | Website address (CORS). `https://` in production. |
| `RESEND_API_KEY` | for email | Resend API key. Used before `SMTP_URL` if both are set. |
| `SMTP_URL` | for email | Alternative to Resend. |
| `MAIL_FROM` | for email | Sender on a domain verified with the email provider. |
| `SENTRY_DSN` | | Error tracking. |
| `STRAVA_CLIENT_ID`, `STRAVA_CLIENT_SECRET` | for Strava | From strava.com/settings/api. |
| `TOKEN_ENCRYPTION_KEY` | with Strava | 32 random bytes (hex or base64). Encrypts stored Strava tokens. |
| `STORAGE_DRIVER` | | `local` (default) or `s3`, plus `AWS_*`. |
| `TRUST_PROXY` | | Proxies in front: `1` locally, `2` for Vercel → Render. |
| `AUTH_RATE_LIMIT` | | Login/sign-up attempts per IP per 15 min (default 20). |
